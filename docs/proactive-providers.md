# Proactive provider ingestion

This is the first Slack/Linear implementation slice, not a deployed or live-provider-certified complete company brain. The knowledge runtime is separate from interactive connected-tool use. It never asks a model to choose or execute provider tools. A verified adapter fetches evidence, the core store stages it, and shared `reasonEvents` proposes facts with bounded retained thread and cross-source context. The core validates exact provenance, version ordering and audience intersections before atomic commit. A connection being usable interactively does not establish scan coverage or a company-wide content grant. Existing Supermemory memory tools remain intact; permission-checked current knowledge lives in the organization's Durable Object SQLite store, not a company-wide memory container.

## Integration contract

The Worker, routes and agent shell now supply these integration hooks:

- Expose the Agents callback `runKnowledgeTick(payload: { orgId: string })`, delegating to `runKnowledgeTick(agent, payload)`.
- Call `ensureKnowledgeSchedule(agent, orgId)` on activation/startup and after connection changes. It ensures one durable, every-minute cron callback. Overdue sources are checked on the next callback after a missed alarm/restart; it does not replay every missed minute.
- Call `discoverKnowledgeSources(agent, orgId)` for explicit discovery when appropriate. A tick also discovers sources. Every connection row and Slack installation is registered, including unsupported connections, without slug deduplication.
- After verifying Slack's request signature, the route persists the complete Events API envelope in a durable inbox before acknowledging. A bounded rotating drain later calls runtime ingestion; unknown channels await discovery without blocking other deliveries. Persistence failure returns a retryable response. Unknown channels are not invented or granted access from a webhook.
- Queries must enforce live source access and every evidence audience. `queryKnowledge` alone is not an authorization API. The parent query/access layer must verify the requesting user's current membership in each Slack channel, the installation's identity and bot membership, and the current personal connection owner. These checks must fail closed when incomplete.

Revocation is terminal in the core store. Reconnects, ownership changes and observed Slack rejoins get fresh runtime source IDs, with no inherited facts or cursors. Old revoked IDs remain revoked. Do not hard-code a source ID as an authorization grant; discover current IDs through the store.

## Linear

Linear uses the existing authenticated MCP client and OAuth refresh path, restricted to the `linear` connection at the official `mcp.linear.app` host. An MCP access token is **not** treated as a Linear REST/GraphQL credential. Only the named `list_issues` tool is eligible for polling, and its live input schema must expose the expected `updatedAt`, `orderBy`, `cursor`, and numeric `limit` arguments. Unknown required arguments, destructive annotations, or incompatible schemas disable this adapter rather than inventing arguments. Tool catalog inspection is read-only and limited to the first catalog page; a tool on a later page is not silently assumed to exist.

Each scan fixes a lower updated-at bound and an observation-time upper watermark. It requests `orderBy: "updatedAt"` and an ISO lower bound; a one-minute overlap protects boundary timestamps. Initial scans begin within the configured backfill period plus that overlap. Results newer than the fixed upper watermark are deferred to the next window. Each committed batch is sorted ascending by version and canonical issue ID, and event text preserves the issue ID, human identifier, status and assignee.

Important ordering limitation: `orderBy: "updatedAt"` alone does not prove ascending server order. The adapter requests ascending only if the live schema explicitly offers a recognized direction parameter with `asc`. Otherwise it sorts each batch locally and advances the window watermark only after explicit pagination completion, not after the newest issue on a page. It does not claim globally ascending page order. Missing or repeated continuation cursors, missing explicit completion metadata, malformed issue versions and oversized pages fail without advancing the cursor. Coverage remains partial.

Personal connections permit only their owner. Org-shared connections default to `{ kind: "users", userIds: [] }` because issue/team ACLs have not been verified. They are not fetched/reasoned over and do not claim successful processing. Issue metadata and a shared tool credential do not prove that every employee can read every issue. Sabari cannot see another employee's personal Linear/Granola data without an explicit audience policy. That sharing policy remains a product decision, not an assumed company-wide grant.

Disclosure also requires a compatible live `get_issue` schema and successful object-access check. Newer live versions withhold cached current facts until background processing catches up; explicit history still requires live access. Optional owner session POST `/brain/knowledge/linear/:connectionId/webhook-config` accepts `{ organizationId, secret, consent: true }` and encrypts the signing secret. Configure the returned `/brain/knowledge/hooks/linear/:connectionId` URL in Linear with that secret. Raw-body HMAC, signed-time and delivery checks precede durable inbox admission. Issue create/update/remove is supported; other entities/comments are not. Provider webhook registration requires appropriate Linear permissions and is NOT performed automatically. Never provide signing secrets in chat or logs.

This adapter's polling coverage excludes deletion reconciliation, inaccessible/private teams, objects outside the initial window, comments and project/document history. A deleted issue is not reliably detectable by polling updated issues; separately wired provider webhooks may extend coverage. Provider schema and pagination behavior are checked at runtime, not inferred from a stale architecture document. Explicit identifiers support core relationship extraction; equal titles are never used as identity.

## Slack

Discovery reads every organization installation and decrypts its existing bot token using `ENCRYPTION_SECRET`. It pages `users.conversations` for actual joined, non-archived public/private channels. Channel discovery rotates across installations and persists its continuation. It revokes disappeared channels only after a complete enumeration, never from an incomplete first page. Installation-level coverage stays visible even when listing fails.

Each channel is a separate source with `{ kind: "slack_channel", teamId, channelId }`. Before polling or staging a webhook, the runtime verifies that the installation still exists and `conversations.info` reports current bot membership. That is an ingestion check, **not** a substitute for the requesting employee's live membership check at query time.

Polling uses the existing non-retrying `getSlackChannelHistoryPage` client, `conversations.history`, and durable cursors over fixed oldest/latest windows. A history rate-limit response pauses polling across the installation's channels, not merely the channel that received the 429. History is not an updated-message feed. It cannot reliably recover edits/deletions to old messages, and channel history does not enumerate all replies. The optional verified Events API hook records new messages, replies to old roots, `message_changed` edits and `message_deleted` tombstones. Object identity is the message timestamp within its channel source; microsecond integer event/edit timestamps order versions. Thread timestamps remain explicit in evidence text.

Known thread roots observed through backfill/replies are reconciled with one fair `conversations.replies` page per callback (15 items/page, bounded 1,000-root registry). Thread-fetch progress is distinct from successful knowledge processing. Unknown roots outside backfill and missed deletion events cannot be fully recovered; actual token scopes/rate limits can prevent replies access. Do not claim complete Slack history or current truth merely because a channel poll succeeded. Coverage is explicitly partial. Original message time is preserved on edits, separately from the ordering version.

Relevant bot scopes include channel/group read scopes for discovery and info, and `channels:history` / `groups:history` for corresponding history. Subscribe to applicable public/private message events. Missing scopes produce bounded errors and limited coverage, not broader credentials or automatic channel joins. Slack's commercial/non-Marketplace history restrictions can limit page sizes and cadence; provider rate limits take precedence over configured cadence.

## Recovery and resource limits

Due work is sorted by oldest attempt and bounded by source, page, event, operation and elapsed-time budgets. Each selected source gets at most one batch/page per tick. Pending staged events always retry before another provider fetch. A separate staged checkpoint remembers the fetched page's destination; the source cursor advances only after its pending chunks commit. If a crash occurs before the checkpoint is recorded, interrupted pages safely replay against the core's durable receipts/version heads. Duplicate pages do not rerun reasoning on already acknowledged events. A successful empty page may advance the checked watermark, but does not update `lastProcessedAt`. New activity/continuations use minimum cadence; quiet sources double cadence up to the maximum. Failures back off and honor surfaced Retry-After metadata, including Slack's HTTP header. Errors persist only fixed codes, never provider exception text, raw responses, credentials or tokens.

Optional `KNOWLEDGE_` bindings accept numbers or numeric strings. Defaults: `MIN_INTERVAL_MS=60000`, `MAX_INTERVAL_MS=3600000`, `BACKFILL_MS=604800000` (7 days), `RETENTION_MS=7776000000` (90 days), `MAX_SOURCES=6`, `MAX_PAGES=6`, `MAX_EVENTS=150`, `PAGE_SIZE=25`, `MAX_SUBREQUESTS=30`, `TICK_MS=25000`. Values are clamped: sources/pages ≤20, events ≤500 per tick, page size ≤100, operation allowance ≤50, initial backfill ≤30 days, retention ≤365 days, and tick admission budget ≤45 seconds. Minimum polling cadence is one minute. Text is clipped per page to stay within the core reasoning/staging byte limits.

The operation budget counts D1 discovery reads, explicit provider requests and model reasoning, with a conservative six-operation reservation per MCP connection for initialization/OAuth/cleanup. It is not transport-level instrumentation: the existing authenticated client may perform additional OAuth exchanges. Deadline signals propagate into model and provider fetches, including MCP setup/OAuth and Slack history; model retries are disabled. Inbox drains have separate bounded admission. Configure lower budgets/headroom where platform limits require it; no retry loop sleeps inside a tick. Durable poll cursors detect multi-page cycles using bounded hashes, reject continuation tokens over 2 KB, and stop safely after 512 continued pages in one window instead of growing state indefinitely. A window exceeding that limit remains partial and requires operator intervention/reinitialization with an appropriate backfill window; no events are silently skipped.

Baseline intervals are Slack 30 minutes, Linear one minute and future meeting adapters two hours, clamped to configured bounds. Activity accelerates checks; idle Linear backs off to at most five minutes. The default maximum is one hour, so a future two-hour meeting baseline needs a larger configured maximum. Worker cron every five minutes bootstraps/repairs organization schedules in rotating sweeps. Provider limits, failed reasoning and large backfills can exceed target freshness: no hard universal delay guarantee is claimed.

Retention runs at most daily through `pruneKnowledge`. The core controls what is pruned: superseded history is eligible; current evidence, deletion/version heads and durable replay receipts may outlive payload retention to prevent resurrection. Runtime does not erase those safety records or claim a full-data TTL.

## Provider references and verification

Granola and other unverified connectors are automatically discovered but remain unsupported for background ingestion. Official Granola MCP documents list `query_granola_meetings`, `list_meeting_folders`, `list_meetings`, `get_meetings`, `get_meeting_transcript`, and `get_account_info`, but do not publish sufficient schemas/pagination/modification/deletion contracts for a safe incremental adapter. Its separate REST API supports `updated_after`, cursors and version/deletion data but needs a different API-key integration; MCP OAuth tokens are not reused there. Next step is authorized capability/audience verification, not invented schemas.

Bots use `sudopedia_query_knowledge` and `sudopedia_source_status`. Equivalent REST routes are POST `/brain/external/v1/knowledge/query` and GET `/brain/external/v1/knowledge/sources`; session health uses GET `/brain/knowledge/sources`. `sourcePage`/`nextSourcePage` paginate five sources to leave room for live permission checks. Cross-source facts spanning different pages may be withheld; large Slack memberships/deadlines can make checks incomplete. Retrieval is bounded lexical ranking, not full semantic search. All supporting evidence must be authorized; recorded state is not proof of active work, absent evidence is not negative proof, and history is not current truth.

Status includes connection state, coverage, last check, last successful processing, processed watermark, delay and fixed error codes. Empty polls can advance the window watermark without falsely updating `lastProcessedAt`. Repeated invalid model proposals remain pending with visible failure and may stall a source; bounded quarantine/operator tooling remains future work. Permanent safety records are not a full-data TTL. Under pressure the store compacts unreferenced processed payloads and superseded history while retaining heads/receipts/tombstones. Fully pinned/pending evidence at 5,000 payloads or more than 10,000 current facts causes explicit capacity failure, without false processing; edits still invalidate and deletes still persist without model work. Permanent safety records continue growing and need operational capacity planning.

Every model output inherits the audience, retained input evidence and invalidation dependencies of ALL supplied evidence, including context it did not cite. Citations cannot broaden access. This conservative boundary can restrict an entire reasoning batch, invalidate unrelated outputs from that batch, or hit fact payload limits with large context; ACL-isolated reasoning and compact shared provenance are future optimizations. Live Slack object existence/content/version is checked before disclosure as well as channel membership, so a missed edit/deletion withholds a cached current fact. Slack and Linear disclosure checks share bounded request budgets and fail closed. Slack webhook draining shares the tick's operation/deadline budget and installation cooldown, including Retry-After. Responses use bounded evidence excerpts after full verification.

## PR audit fixes

Reasoning captures an immutable batch/context/source-policy snapshot before the model call. Commit rejects the entire inference if any input is edited, deleted, replaced, processed concurrently, revoked, or has a changed audience; it never drops a private input and publishes the remainder. Runtime reasoning uses at most three staged events plus two context objects per call. Fetched pages drain in these smaller chunks; cursor and page watermark advance only after all pending evidence is committed. Every supplied input remains an access/invalidation dependency.

Disclosure caches each source's verified MCP get-tool catalog within the request and uses a bounded 40-operation evidence budget, enough for five distinct sources including conservative setup reservations. Tests exercise a 25-issue page through the real store/access/query/verifier with mocked provider transport, rather than mocking authorization/verification away. Provider failures/deadlines still withhold evidence rather than bypass checks.

Slack evidence retains a SHA-256 fingerprint of full normalized content before clipping/redaction, plus a provider content-edit version distinct from delivery ordering. Live comparison uses these values; long messages and redaction no longer create false mismatches. Fingerprints are not returned in query excerpts. Legacy evidence uses conservative redacted-prefix and version checks.

Linear webhook configuration and admitted deliveries are bound to the current discovered source, owner and a hash of live credential-generation fields. Legacy unbound rows fail closed. Old deliveries are scrubbed rather than reassigned after reconnect/owner changes. Credential changes, including OAuth refresh, conservatively require source rediscovery and webhook reconfiguration; automatic webhook renewal is not implemented. Incremental polling remains the recovery path.

Slack revoked/invalid deliveries are terminally scrubbed. Unknown-source deliveries have a 24-hour quarantine, after which bodies are scrubbed and durable channel/installation coverage flags record the recovery gap; no successful knowledge watermark is claimed. Admission also reclaims expired/revoked backlog so it cannot permanently consume the entire inbox. Retryable provider failures honor Retry-After.

One absolute eight-second deadline spans Worker agent lookup, RPC dispatch, permission checks and live evidence verification. An actor-bound request identity carries cancellation to the Durable Object; a late cancellation cannot cancel another actor's request. Individual waits are bounded even when a local D1/RPC promise itself cannot be cancelled, and no later phase receives a fresh budget.
